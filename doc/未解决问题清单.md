`src-tauri/src/service/problem/mod.rs`；夹具标注见
`src-tauri/src/adapter/hoj/tests/mod_tests.rs`（多处「按文档构造，未经真实联调校正」）。

**现状（2026-09-22 核查）**：仍按文档实现 + 宽松容错，HOJ 侧夹具中除

以下核对点只能靠联调确认：

4. `get-user-problem-status` 的返回键是 pid 字符串还是数字，值域是否只有 0/1/2。
5. `get-contest-problem-details` 的 `timeLimit / memoryLimit / stackLimit` 单位与语言倍率是否如文档所述（C/C++ 1 倍、其它 ×2）。
6. `post_json_authed` 的 Refresh-Token 轮换在每 10s 一次的榜单请求下是否稳定（轮换失效会表现为周期性 401）。
7. `get-contest-announcement` 的 `AnnouncementVO` 实际字段名（id/title/content/uid/username/createTime/updateTime）与时间格式。
8. `contest-submissions` 的 JudgeVO 列表形态（`completeProblemID=true` 时 `displayId` 是否确实回填；`beforeContestSubmit` 必填语义）。
9. `get-all-case-result` 的 `subTaskJudgeCaseVoList` 实际结构（当前按 `{groupNum, judgeCaseList}` 宽松解析）与 `judgeCaseMode` 值域。
10. `get-submission-detail` 完整映射（code/errorMessage/judger/oiRankScore 的实际 null 分布）。
11. `oiRankScoreType` 的实际取值（"Recent"/"Highest" 大小写与缺省行为）。

**处理建议**：联调时逐项核对；把脱敏后的真实响应 JSON 存为测试夹具
（照 `contest_list_anon.json` 的做法：只替换自由文本，保留键名与 null 分布），
