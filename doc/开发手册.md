# Hinina 项目开发手册（初稿）

> 本手册用于统一项目目标、技术选型与研发约束，便于后续开发、协作与维护。

## 1. 项目概述

### 1.1 项目名称
- Hinina

### 1.2 项目目的
- 为本校的程序设计竞赛校赛制作一款美观、功能集成、界面高度可定义的OJ客户端。

### 1.3 项目意义
- 通过兼容层兼容多个开源OJ系统（例如HOJ、HUSTOJ等）的竞赛功能，提供统一、美观的交互界面。
- 高度可定义，提升校赛参赛者的使用体验。

## 2. 范围与目标

### 2.1 当前阶段目标（MVP 版本核心功能）
定位为**比赛客户端（Contest Client）**，而不是完整 OJ。MVP 版本必须聚焦以下 5 个核心功能闭环：
1. 登录 (Login)
2. 获取比赛 (Get Contests)
3. 查看题目 (View Problems)
4. 提交代码 (Submit Code)
5. 查看评测结果 (View Judgement Results)

### 2.2 非目标
- MVP 阶段不包含以下能力（由目标 OJ 服务端提供）：
  - 用户注册
  - 题库管理
  - OJ 管理后台
- 后期规划能力：
  - 客户端管理后台（界面定制、OJ 类型与地址配置、比赛切换、插件管理等）

## 3. 技术选型与原因（待补充）

### 3.1 技术栈
- **前端 (Frontend)**：Vue3, Vite, TypeScript, Pinia, TailwindCSS, Naive UI
- **编辑器组件 (Editor)**：Monaco Editor
- **后端/客户端框架 (Backend)**：Tauri 2, Rust
- **网络通信 (Network)**：Reqwest
- **基础设施库 (Infrastructure)**：Serde, Anyhow, Thiserror, Tracing
- **数据存储 (Database)**：无（作为客户端工具，且无复杂开发需求需要引入路由等功能，不引入 SQL 数据库，而是依赖完善的 Rust 基础设施处理状态和数据）

### 3.2 选型原因

**性能与稳定性**
- **Tauri 2 + Rust**：相较 Electron，Tauri 复用操作系统原生 WebView，二进制体积小、内存占用低，启动快。Rust 提供零成本抽象与内存安全保证，适合作为本地客户端运行时，避免 GC 带来的延迟抖动，保证 UI 线程的流畅响应。
- **Monaco Editor**：作为 VS Code 同源编辑器组件，提供语法高亮、智能补全、代码折叠等完整编辑体验，满足竞赛编程场景下的代码编写需求。
- **无 SQL 数据库**：项目无需本地路由或复杂查询，使用 Rust 类型系统配合文件存储管理配置与状态，避免引入数据库依赖带来的打包体积和维护负担。

**开发效率**
- **Vue3 + Vite + TypeScript**：Vue3 的响应式系统与模板语法天然适合拖拽式布局和配置驱动型界面，配合 Composition API 和 Pinia 实现灵活的状态管理。Vite 提供极快的 HMR 与构建速度，TypeScript 保障前端类型安全。
- **Tauri 2**：提供完善的跨平台 API（窗口管理、文件系统、系统托盘等），与前端通过 IPC 通信，前后端职责清晰，降低联调成本。

**维护成本**
- **Rust 生态（Serde / Anyhow / Thiserror / Tracing）**：使用 Rust 社区成熟的基础设施库，序列化、错误处理、日志追踪均有标准方案，减少造轮子开销。
- **Naive UI**：与 Vue3 深度集成的组件库，Tree Shaking 友好，按需引入降低打包体积。

## 4. 约束与技术路线（待补充）

### 4.1 约束条件
- 时间约束：无严格交付时间线，灵活迭代开发。
- 人力约束：由 `dongzhuo375` 担任项目负责人/核心开发者，主导一切架构设计、技术选型与功能开发。
- 运行环境与基础设施约束：
  - 本项目为桌面客户端，**不依赖专用服务器、数据库或容器化基础设施**。
  - **首发目标环境**：系统主要运行于 **Windows 桌面环境**。未来可根据需要扩展对 Linux 与 macOS 平台的支持。
  - **网络限制**：通过网络直接访问目标 OJ 平台，要求能够正常访问目标 OJ 的 Web/API 服务。
  - **本地权限要求**：客户端需要具备本地文件读写能力，用于保存用户配置、工作区代码及缓存数据。

### 4.2 技术路线
- **架构模式**：整体采用 **Clean Architecture（整洁架构）**，Rust 端分层解耦，前端采用 **MVVM** 模式，前后端通过 Tauri IPC 通信。
- **核心设计**：**OJ Adapter 抽象层 (`trait OJProvider`)**
  - 为实现对多个开源 OJ 系统的兼容，通过 Provider Adapter 模式设计良好的 `OJProvider` 抽象层。
  - 只要该抽象层设计完成，后续接入不同 OJ 时只需新增对应的 Provider 实现，而无需重写整个客户端的代码逻辑。
  - **必须兼容的外部系统**：
    - Hydro Online Judge (HOJ)
    - Qingdao University Online Judge (QDUOJ)
    - HUSTOJ 及其衍生实现
    - 支持标准 HTTPS 通信协议的 OJ Web/API 服务
- **模块划分**：

  **Rust 后端（Clean Architecture 分层）**
  | 层次 | 模块 | 职责 |
  |------|------|------|
  | Domain | `core` | 核心实体（Contest、Problem、Submission、User）、`OJProvider` trait 定义 |
  | Application | `service` | 业务用例编排（登录流程、获取题目、提交代码、轮询评测） |
  | Adapter | `adapter` | OJ 适配实现（HOJ、QDUOJ、HUSTOJ），每个 OJ 一个独立的 Provider |
  | Infrastructure | `infra` | HTTP 客户端（Reqwest）、本地配置读写、缓存管理、日志追踪 |

  **Vue3 前端（MVVM 模式）**
  | 层 | 模块 | 职责 |
  |------|------|------|
  | View | `views` / `components` | 登录页、比赛列表、题目阅读器、代码编辑器、提交结果面板 |
  | ViewModel | `stores` (Pinia) | AuthStore、ContestStore、ProblemStore、SubmissionStore |
  | Bridge | `tauri` invoke | 封装 Tauri IPC 调用，连接前端 ViewModel 与 Rust Application 层 |

## 5. 质量、非功能性需求与协作规范
5.1 非功能性需求 (NFRs)
- **性能要求**：
  - 系统应保证常用操作具有良好的响应速度。
  - 客户端启动时间不超过 3 秒。
  - 本地界面操作（界面切换、题面展示、代码编辑等）响应时间不超过 200ms。
  - 网络请求性能受目标 OJ 影响，但客户端应提供加载状态提示并避免阻塞界面。
  - 题面加载和提交结果查询应在网络允许条件下及时完成。
- **可用性要求**：
  - 系统具备基本容错能力，在网络异常、OJ 服务异常或客户端异常退出情况下，保证用户代码和配置数据不丢失。
  - 自动保存用户代码。
  - 支持异常退出后的工作区恢复。
  - 网络异常时提供明确错误提示。
  - 已加载题面可进行本地缓存；题目切换后保留切换前题目工作区内的代码。
- **安全性要求**：
  - 保证用户账号信息和会话信息的安全存储，不记录密码明文。
  - 日志记录避免泄露账号、Cookie 等敏感信息。
  - 可选实现所有网络通信采用 HTTPS。
  - 本地配置文件仅保存必要的用户数据。

### 5.2 代码质量

**代码评审规范**
- 主分支（`main`）启用分支保护，禁止直接推送，所有变更通过 Pull Request 合并。
- PR 提交前需通过 CI 检查（构建、Lint、测试）。
- 评审清单：逻辑正确性、边界处理、错误处理完备性、与现有架构一致性、敏感信息无泄露。
- 单人项目采用自审为主、辅助 AI Review 的方式，关键模块变更需额外留存设计记录。

**测试策略**
| 层级 | 技术 | 覆盖范围 |
|------|------|---------|
| Rust 单元测试 | `cargo test` | Domain 层实体逻辑、`OJProvider` trait 默认实现 |
| Rust 集成测试 | `cargo test` (tests/) | 各 OJ Adapter 的请求/响应解析、Service 层编排流程 |
| 前端单元测试 | Vitest + Vue Test Utils | Pinia Store 逻辑、关键组件行为 |
| 前端 E2E 测试 | Tauri + Playwright（或 WebDriver） | 5 大核心功能闭环的端到端验证，使用 Mock OJ 后端 |

### 5.3 协作流程

**团队角色**
- `dongzhuo375` 担任项目负责人，享有架构与技术选型最终决定权。

**分支策略（GitHub Flow）**
- `main` 为受保护分支，始终保持可发布状态。
- 所有开发工作在功能分支上进行，命名规范：`feat/<描述>`、`fix/<描述>`、`docs/<描述>`、`chore/<描述>`。
- 合并前必须通过 Pull Request，至少一人 Review 通过后方可合并。
- 合并方式推荐 Squash Merge，保持 `main` 的提交历史干净、可读。

**发布流程（CI 自动发布）**
- 推送语义化版本标签（如 `v0.1.0`）触发 GitHub Actions 工作流。
- CI 自动执行构建→测试→打包（Windows/macOS/Linux）→发布到 GitHub Release。
- 发版前确保 CHANGELOG 已更新，Release 说明中包含变更摘要与已知问题。

## 6. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 目标 OJ API 无公开文档或不稳定 | `OJProvider` 适配层开发受阻，需反复逆向工程 | 优先选取文档最完善的 OJ（如 HOJ）作为首个适配目标，验证 Provider trait 设计的通用性后再扩展 |
| `OJProvider` trait 抽象层次设计不当 | 接入新 OJ 时需频繁重构，破坏已有适配实现 | 在实现首个 Adapter 之后、接入第二个 OJ 之前，基于至少两个 OJ 的实际差异重新审视 trait 边界 |
| Tauri 2 版本快速迭代，API 变动 | 升级时出现 Breaking Change，阻塞开发 | 锁定大版本，非必要不升级；关注 Release Notes，评估后再升级 |
| 团队 Rust 经验不足 | 后端开发效率低，错误处理不规范 | 核心逻辑优先在 Domain/Application 层以纯 Rust 实现，Infrastructure 层可适度使用前端能力兜底 |
| 跨平台兼容性（后期扩展 Linux/macOS） | Windows 可用但其他平台存在渲染或系统 API 差异 | 全程使用 Tauri 官方跨平台 API，避免引入平台特定依赖；CI 中启用多平台构建提前暴露问题 |
