# Hinina 项目开发手册（初稿）

> 本手册用于统一项目目标、技术选型与研发约束，便于后续开发、协作与维护。

## 1. 项目概述

### 1.1 项目名称
- Hinina

### 1.2 项目目的
- 为本校的程序设计竞赛校赛制作一款美观、功能集成、界面高度可定义的OJ客户端。

### 1.3 项目意义
- 通过兼容层屏蔽多个开源 OJ 系统（HOJ、QDUOJ、HUSTOJ 等）的差异，为竞赛选手提供统一的答题与评测体验。
- 面向 ACM/ICPC、XCPC 及校赛等场景，以 OJ 竞赛客户端为核心定位，不扩展为通用 IDE 或代码编辑平台。

## 2. 范围与目标

### 2.1 当前阶段目标（MVP 版本核心功能）
定位为**比赛客户端（Contest Client）**，而不是完整 OJ。MVP 版本必须聚焦以下 5 个核心功能闭环：
1. 登录 (Login)
2. 获取比赛 (Get Contests)
3. 查看题目 (View Problems)
4. 提交代码 (Submit Code)
5. 查看评测结果 (View Judgement Results)

### 2.2 非目标
- MVP 阶段不包含以下能力（由目标 OJ 服务端提供）：
  - 用户注册
  - 题库管理
  - OJ 管理后台
- 后期规划能力：
  - 客户端管理后台（界面定制、OJ 类型与地址配置、比赛切换、插件管理等）

## 3. 技术选型与原因

### 3.1 技术栈
- **前端 (Frontend)**：Vue3, Vite, TypeScript, Pinia, TailwindCSS, Naive UI
- **编辑器组件 (Editor)**：Monaco Editor
- **后端/客户端框架 (Backend)**：Tauri 2, Rust
- **网络通信 (Network)**：Reqwest
- **基础设施库 (Infrastructure)**：Serde, Anyhow, Thiserror, Tracing
- **数据存储 (Database)**：无（作为客户端工具，且无复杂开发需求需要引入路由等功能，不引入 SQL 数据库，而是依赖完善的 Rust 基础设施处理状态和数据）

### 3.2 选型原因

**性能与稳定性**
- **Tauri 2 + Rust**：相较 Electron，Tauri 复用操作系统原生 WebView，二进制体积小、内存占用低，启动快。Rust 提供零成本抽象与内存安全保证，适合作为本地客户端运行时，避免 GC 带来的延迟抖动，保证 UI 线程的流畅响应。
- **Monaco Editor**：作为 VS Code 同源编辑器组件，提供语法高亮、智能补全、代码折叠等完整编辑体验，满足竞赛编程场景下的代码编写需求。
- **无 SQL 数据库**：项目无需本地路由或复杂查询，使用 Rust 类型系统配合文件存储管理配置与状态，避免引入数据库依赖带来的打包体积和维护负担。

**开发效率**
- **Vue3 + Vite + TypeScript**：Vue3 的响应式系统与模板语法天然适合拖拽式布局和配置驱动型界面，配合 Composition API 和 Pinia 实现灵活的状态管理。Vite 提供极快的 HMR 与构建速度，TypeScript 保障前端类型安全。
- **Tauri 2**：提供完善的跨平台 API（窗口管理、文件系统、系统托盘等），与前端通过 IPC 通信，前后端职责清晰，降低联调成本。

**维护成本**
- **Rust 生态（Serde / Anyhow / Thiserror / Tracing）**：使用 Rust 社区成熟的基础设施库，序列化、错误处理、日志追踪均有标准方案，减少造轮子开销。
- **Naive UI**：与 Vue3 深度集成的组件库，Tree Shaking 友好，按需引入降低打包体积。

## 4. 约束与技术路线

### 4.1 约束条件
- 时间约束：无严格交付时间线，灵活迭代开发。
- 人力约束：由 `dongzhuo375` 担任项目负责人/核心开发者，主导一切架构设计、技术选型与功能开发。
- 运行环境与基础设施约束：
  - 本项目为桌面客户端，**不依赖专用服务器、数据库或容器化基础设施**。
  - **首发目标环境**：系统主要运行于 **Windows 桌面环境**。未来可根据需要扩展对 Linux 与 macOS 平台的支持。
  - **网络限制**：通过网络直接访问目标 OJ 平台，要求能够正常访问目标 OJ 的 Web/API 服务。
  - **本地权限要求**：客户端需要具备本地文件读写能力，用于保存用户配置、工作区代码及缓存数据。

### 4.2 技术路线

**架构模式**
- 整体采用 **Clean Architecture（增强版）**：Rust 端分层解耦，前端采用 **MVVM** 模式，前后端通过 Tauri IPC 通信。
- 架构的设计原则是保持 MVP 简洁、单人可维护，同时预留扩展空间（插件），避免过度设计。
- Micro Kernel 架构作为远期演进方向记录，当前阶段不采用。

**核心领域对象**
| 实体 | 说明 |
|------|------|
| `User` | 用户身份与会话 |
| `Contest` | 比赛信息 |
| `Problem` | 题目详情 |
| `Submission` | 提交与评测记录 |
| `Workspace` | 工作区（代码存储、自动保存、崩溃恢复、比赛隔离、模板管理、缓存、插件数据） |

`Workspace` 是客户端最核心的对象之一，未来的插件系统和本地评测均围绕 Workspace 展开。

**OJProvider 拆分为组合接口**

为避免单一巨型 trait，将 OJ 适配拆分为独立的小接口，各 Adapter 按需组合实现：

```
trait AuthProvider       // 登录、登出、会话管理
trait ContestProvider    // 获取比赛列表与详情
trait ProblemProvider    // 获取题目描述、样例
trait SubmissionProvider // 提交代码、查询评测结果
```

例如 `HOJAdapter` 同时实现以上四个 trait。后续新增 Adapter 时，可先只实现部分接口（以 `ProviderSet` 的 `Option` 字段注册，缺失能力查询时报 `ProviderNotFound`），逐步完善。

**OJ 身份、配置与注册均为数据**

接入一个新 OJ **不修改领域层**：OJ 身份是 `OjId`（字符串，会话文件名 `sessions/{id}.json`），不是编译期枚举；配置按 `OjInstance{id, baseUrl, enabled, options}` 实例清单组织（`oj.active` 指向当前实例，`contest_ref` 为不透明比赛引用）；适配器经 `AdapterFactory{id, build}` 工厂自注册进 `factories()` 清单。接入成本 = 1 个 adapter 子目录 + 工厂清单一行 + 配置一条实例。OJ 切换走显式 `switch_oj` 命令（切 Registry + 持久化 + 发布 `OJSwitched` 事件），与登录解耦；适配器构造依赖 `AdapterDeps` 只准 infra（http/事件总线/存储），禁止依赖 Service 层。

**Event 模块（核心解耦机制）**

在 `core` 中新增 `event` 模块，定义 `AppEvent` 枚举，用于主程序内部解耦及插件共享事件流：

```
LoginSuccess / Logout
ContestChanged
ProblemOpened / ProblemChanged
SubmissionCreated / SubmissionFinished
JudgeUpdated
WorkspaceLoaded / FileSaved
```

遵循原则：**查询与命令走 Service，状态变更走 EventBus**。禁止将所有业务逻辑事件化。

**前端新增 Service 层**

前端分层由 `View → Store → Bridge` 调整为 `View → Store → Service → Bridge`：
- `Store`（Pinia）仅负责状态管理，不放网络请求、数据转换、缓存逻辑或业务流程
- `Service` 层封装所有业务逻辑（`contest.service.ts`、`problem.service.ts`、`submission.service.ts`、`workspace.service.ts`）
- `Bridge` 层封装 Tauri IPC 调用

**新增 ConfigService**

统一管理用户配置、OJ 配置、编辑器偏好、主题、布局及插件配置，避免配置逻辑分散。

**新增 ThemeService**

独立于 ConfigService，负责主题切换、配色方案、字体、圆角等 UI 参数管理，为后续主题扩展预留接口。

**兼容的外部系统**
- Hydro Online Judge (HOJ)
- Qingdao University Online Judge (QDUOJ)
- HUSTOJ 及其衍生实现
- 支持标准 HTTPS 协议的 OJ Web/API 服务

## 5. 质量、非功能性需求与协作规范
5.1 非功能性需求 (NFRs)
- **性能要求**：
  - 系统应保证常用操作具有良好的响应速度。
  - 客户端启动时间不超过 3 秒。
  - 本地界面操作（界面切换、题面展示、代码编辑等）响应时间不超过 200ms。
  - 网络请求性能受目标 OJ 影响，但客户端应提供加载状态提示并避免阻塞界面。
  - 题面加载和提交结果查询应在网络允许条件下及时完成。
  - 客户端按**数据可变性**分层使用轮询与缓存，避免对同一份不变数据反复请求：
    不会变的数据（比赛元信息、题面、终态提交详情/测试点）走缓存；只由本人动作
    改变的数据（我的题目状态）走增量失效 + 按需重拉；随时可能被别人改变的数据
    （榜单名次、评测中状态、公告）只轮询，最多做同查询去抖。判据与失效路径见
    `doc/Architecture.md` 的「客户端缓存策略」。
- **可用性要求**：
  - 系统具备基本容错能力，在网络异常、OJ 服务异常或客户端异常退出情况下，保证用户代码和配置数据不丢失。
  - 自动保存用户代码。
  - 支持异常退出后的工作区恢复。
  - 网络异常时提供明确错误提示。
  - 已加载题面可进行本地缓存（内存 + 磁盘，TTL 30 分钟，默认开启、可在设置页「OJ」分组关闭）；题目切换后保留切换前题目工作区内的代码。
- **安全性要求**：
  - 保证用户账号信息和会话信息的安全存储，不记录密码明文。
  - 日志记录避免泄露账号、Cookie 等敏感信息。
  - 可选实现所有网络通信采用 HTTPS。
  - 本地配置文件仅保存必要的用户数据。

**测试策略**
| 层级 | 技术 | 覆盖范围 |
|------|------|---------|
| Rust 单元测试 | `cargo test` | Domain 层实体逻辑、各 Provider trait 默认实现 |
| Rust 集成测试 | `cargo test` (tests/) | 各 OJ Adapter 的请求/响应解析、Service 层编排流程 |
| 前端单元测试 | Vitest + Vue Test Utils | Pinia Store 逻辑、关键组件行为 |
| 前端 E2E 测试 | Tauri + Playwright（或 WebDriver） | 5 大核心功能闭环的端到端验证，使用 Mock OJ 后端 |

**前端测试文件组织**

单元测试与被测源文件分离，放置于同层目录下的 `__tests__/` 子目录，命名 `{module}.spec.ts`：

```
src/utils/
├── session-check.ts
└── __tests__/
    └── session-check.spec.ts
```

约定：
- 测试环境为 `node`，不引入 jsdom；需要 DOM API（如 `localStorage`）时用 `vi.stubGlobal` 打桩
- IPC 边界一律在 Bridge 层打桩（`vi.mock('@tauri-apps/api/core')`），单元测试不依赖真实 Rust 后端或 OJ 服务器
- 逐层隔离：测 Store 时 mock 其直接下游 Service，测 Service 时 mock 其直接下游 Bridge。"能否只 mock 一层就测"本身即分层是否正确的判据
- 时间与随机数通过参数注入（如 `planNextPrecheck(nowMs, startMs, rand)`），避免依赖 fake timers
- 运行：`npm test`（`vitest run`）；配置位于 `vite.config.ts` 的 `test` 字段
- 当前覆盖纯函数（`utils/`）、跨端错误契约（`bridge/`）与 Store/Service 状态机；组件测试（`@vue/test-utils`）尚未引入

**Rust 测试文件组织**

单元测试代码与源文件分离，放置于同模块目录下的 `tests/` 子目录，通过 `#[path]` 属性引用：

```
src/infra/
├── storage.rs                          → #[cfg(test)] #[path = "tests/storage_tests.rs"] mod tests;
└── tests/
    └── storage_tests.rs
```

约定：
- 测试文件命名：`{module_name}_tests.rs`
- 源文件引用方式：`#[cfg(test)] #[path = "tests/xxx_tests.rs"] mod tests;`
- 测试文件以 `use super::*;` 开头，可访问源文件内的 private 项
- 禁止使用 `src-tauri/tests/` 顶层集成测试目录覆盖单元测试职责，该目录仅用于跨模块集成测试

## 6. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 目标 OJ API 无公开文档或不稳定 | OJ Adapter 层开发受阻，需反复逆向工程 | 优先选取文档最完善的 OJ（如 HOJ）作为首个适配目标，验证组合 trait 设计的通用性后再扩展 |
| OJ 组合 trait 抽象粒度设计不当 | 接入新 OJ 时需频繁重构，破坏已有适配实现 | 完成首个 Adapter 后，接入第二个 OJ 前，基于两者差异审视 trait 边界 |
| Tauri 2 版本快速迭代，API 变动 | 升级时出现 Breaking Change，阻塞开发 | 锁定大版本，非必要不升级；关注 Release Notes 评估后再升级 |
| 团队 Rust 经验不足 | 后端开发效率低，错误处理不规范 | 核心逻辑优先在 Domain/Application 层以纯 Rust 实现，Infrastructure 层适度使用前端能力兜底 |
| 跨平台兼容性（后期扩展 Linux/macOS） | Windows 可用但其他平台存在渲染或系统 API 差异 | 全程使用 Tauri 官方跨平台 API，避免引入平台特定依赖；CI 启用多平台构建提前暴露问题 |

## 7. 插件系统架构

### 7.1 定位

插件系统属于扩展能力，不应取代核心业务（Contest、Problem、Submission、Workspace）。插件为 OJ 客户端提供增强功能，不改变主程序的核心职责。

### 7.2 模块结构

```
plugin/
  host/        — 插件生命周期管理（扫描、加载、启用、禁用、卸载）
  api/         — 对插件暴露的统一 API
  permission/  — 权限校验
  registry/    — 插件注册与发现
  runtime/     — 插件运行时（v1.0+ 实现）
```

### 7.3 Plugin Host

`PluginHost` 在应用启动时初始化，负责扫描插件目录、加载 Manifest、注册插件。启动流程：

```
Application → PluginHost.start() → 扫描 plugins/ → 加载插件
```

### 7.4 Plugin API

插件**禁止**直接访问内部 Service（WorkspaceService、ProblemService 等），只能通过 Plugin API：

```
plugin/api/
  workspace.rs   — hinina.workspace.read() / write()
  problem.rs     — hinina.problem.current()
  contest.rs     — hinina.contest.current()
  ui.rs          — 侧边栏、命令面板等 UI 扩展
  event.rs       — 事件订阅
```

插件永远不感知内部实现细节。

### 7.5 权限系统

采用最小权限原则。插件在 Manifest 中声明所需权限，所有 API 调用经过 `Permission` 层校验：

```json
{
  "permissions": ["workspace.read", "workspace.write", "problem.read"]
}
```

权限示例：`WorkspaceRead`、`WorkspaceWrite`、`ProblemRead`、`ContestRead`、`Notification`。

### 7.6 EventBus 与插件

插件不单独维护事件系统，共享核心 EventBus。`PluginHost` 负责将 `AppEvent` 转发为 `PluginEvent`。插件可监听 `problem.changed`、`submission.finished`、`contest.started` 等事件。

### 7.7 扩展点

预留以下 UI 扩展点，未来插件通过注册扩展点增强界面：

| 扩展点 | 用途 |
|--------|------|
| `SidebarExtension` | 侧边栏面板（排行榜、公告等） |
| `CommandExtension` | 命令面板注册 |
| `StatusBarExtension` | 状态栏信息 |
| `EditorExtension` | Monaco Editor 增强 |

| 阶段 | 内容 |
|------|------|
| **当前 (v0.x)** | 仅预留插件架构设计，不实现运行时。保留 `PluginHost`、`PluginApi`、`Permission`、`ExtensionPoint` 等模块的接口定义 |
| **v1.0** | 实现 JavaScript / TypeScript 插件运行时。插件目录：`plugins/<name>/manifest.json` + `index.js`。典型场景：公告助手、模板管理、排行榜增强、比赛提醒 |
| **v2.0** | 引入 WASM 插件运行时，支持 Rust → WASM 高性能插件。典型场景：AST 分析、代码补全、静态检查、本地评测扩展 |

## 9. 推荐目录结构

```
src-tauri/
  core/
    entity/       — User, Contest, Problem, Submission, Workspace
    provider/     — AuthProvider, ContestProvider, ProblemProvider, SubmissionProvider
    event/        — AppEvent, EventBus
  service/
    auth/
    contest/
    problem/
    submission/
    workspace/
    config/
    theme/
  adapter/
    hoj/
    qduoj/
    hustoj/
  infra/
    http/
    storage/
    cache/
    logger/
  plugin/
    host/
    api/
    permission/
    registry/
    runtime/

src/                   — Vue3 前端
  views/
  components/
  stores/
  services/
  bridge/
```

此架构的核心目标：保持 MVP 简洁、单人可维护、Workspace First 设计、EventBus 解耦、预留插件扩展空间，同时避免过度设计导致未来推倒重构。
