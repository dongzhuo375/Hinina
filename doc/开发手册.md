# Hinina 项目开发手册（初稿）

> 本手册用于统一项目目标、技术选型与研发约束，便于后续开发、协作与维护。

## 1. 项目概述

### 1.1 项目名称
- Hinina

### 1.2 项目目的
- 为本校的程序设计竞赛校赛制作一款美观、功能集成、界面高度可定义的OJ客户端。

### 1.3 项目意义
- 通过兼容层屏蔽多个开源 OJ 系统（HOJ、QDUOJ、HUSTOJ 等）的差异，为竞赛选手提供统一的答题与评测体验。
- 面向 ACM/ICPC、XCPC 及校赛等场景，以 OJ 竞赛客户端为核心定位，不扩展为通用 IDE 或代码编辑平台。

## 2. 范围与目标

### 2.1 当前阶段目标（MVP 版本核心功能）
定位为**比赛客户端（Contest Client）**，而不是完整 OJ。MVP 版本必须聚焦以下 5 个核心功能闭环：
1. 登录 (Login)
2. 获取比赛 (Get Contests)
3. 查看题目 (View Problems)
4. 提交代码 (Submit Code)
5. 查看评测结果 (View Judgement Results)

### 2.2 非目标
- MVP 阶段不包含以下能力（由目标 OJ 服务端提供）：
  - 用户注册
  - 题库管理
  - OJ 管理后台
- 后期规划能力：
  - 客户端管理后台（界面定制、OJ 类型与地址配置、比赛切换、插件管理等）

## 3. 技术选型与原因

### 3.1 技术栈
- **前端 (Frontend)**：Vue3, Vite, TypeScript, Pinia, TailwindCSS, Naive UI
- **编辑器组件 (Editor)**：Monaco Editor
- **后端/客户端框架 (Backend)**：Tauri 2, Rust
- **网络通信 (Network)**：Reqwest
- **基础设施库 (Infrastructure)**：Serde, Anyhow, Thiserror, Tracing
- **数据存储 (Database)**：无（作为客户端工具，且无复杂开发需求需要引入路由等功能，不引入 SQL 数据库，而是依赖完善的 Rust 基础设施处理状态和数据）

### 3.2 选型原因

**性能与稳定性**
- **Tauri 2 + Rust**：相较 Electron，Tauri 复用操作系统原生 WebView，二进制体积小、内存占用低，启动快。Rust 提供零成本抽象与内存安全保证，适合作为本地客户端运行时，避免 GC 带来的延迟抖动，保证 UI 线程的流畅响应。
- **Monaco Editor**：作为 VS Code 同源编辑器组件，提供语法高亮、智能补全、代码折叠等完整编辑体验，满足竞赛编程场景下的代码编写需求。
- **无 SQL 数据库**：项目无需本地路由或复杂查询，使用 Rust 类型系统配合文件存储管理配置与状态，避免引入数据库依赖带来的打包体积和维护负担。

**开发效率**
- **Vue3 + Vite + TypeScript**：Vue3 的响应式系统与模板语法天然适合拖拽式布局和配置驱动型界面，配合 Composition API 和 Pinia 实现灵活的状态管理。Vite 提供极快的 HMR 与构建速度，TypeScript 保障前端类型安全。
- **Tauri 2**：提供完善的跨平台 API（窗口管理、文件系统、系统托盘等），与前端通过 IPC 通信，前后端职责清晰，降低联调成本。

**维护成本**
- **Rust 生态（Serde / Anyhow / Thiserror / Tracing）**：使用 Rust 社区成熟的基础设施库，序列化、错误处理、日志追踪均有标准方案，减少造轮子开销。
- **Naive UI**：与 Vue3 深度集成的组件库，Tree Shaking 友好，按需引入降低打包体积。

## 4. 约束与技术路线

### 4.1 约束条件
- 时间约束：无严格交付时间线，灵活迭代开发。
- 人力约束：由 `dongzhuo375` 担任项目负责人/核心开发者，主导一切架构设计、技术选型与功能开发。
- 运行环境与基础设施约束：
  - 本项目为桌面客户端，**不依赖专用服务器、数据库或容器化基础设施**。
  - **首发目标环境**：系统主要运行于 **Windows 桌面环境**。未来可根据需要扩展对 Linux 与 macOS 平台的支持。
  - **网络限制**：通过网络直接访问目标 OJ 平台，要求能够正常访问目标 OJ 的 Web/API 服务。
  - **本地权限要求**：客户端需要具备本地文件读写能力，用于保存用户配置、工作区代码及缓存数据。

### 4.2 技术路线

**架构模式**
- 整体采用 **Clean Architecture（增强版）**：Rust 端分层解耦，前端采用 **MVVM** 模式，前后端通过 Tauri IPC 通信。
- 架构的设计原则是保持 MVP 简洁、单人可维护，同时预留扩展空间（插件），避免过度设计。
- Micro Kernel 架构作为远期演进方向记录，当前阶段不采用。

**核心领域对象**
| 实体 | 说明 |
|------|------|
| `User` | 用户身份与会话 |
| `Contest` | 比赛信息 |
| `Problem` | 题目详情 |
| `Submission` | 提交与评测记录 |
| `Workspace` | 工作区（代码存储、自动保存、崩溃恢复、比赛隔离、模板管理、缓存、插件数据） |

**代码落盘语义（Workspace 持久化契约）**

落盘采用 **debounce-to-memory**：编辑器改动经 2 秒防抖推送到**后端内存**
（`update_workspace_file` 只写内存、不写盘），磁盘写入只有两条路径 —— 显式
`save_workspace` 与后台 auto-save 周期。如此「自动保存间隔」才真正决定落盘频率
（写透语义下该配置形同虚设）。五条硬约定：

1. **内存是唯一权威副本**：`WorkspaceManager::update_file` 只改内存并标脏；
   `create` / `load` / `switch` 替换当前工作区前必须先落盘旧的
   （`save_current_if_dirty`），否则未落盘的改动随替换静默消失。
2. **落盘时机由调用点编排**：切题、窗口失焦、页面隐藏、离开解题页
   （`ProblemSolveView`）与关窗（`main.ts` 的 `onCloseRequested` 握手）——
   auto-save 周期最长 300 秒，这些时刻只靠周期就会丢改动。
3. **auto-save 以修订号判定能否清脏，且取快照与写盘整体在读锁内完成**：读锁与
   `save()` / `update_file` 的写锁互斥，保证「旧快照的写」不可能落在「更新的写」
   之后（否则磁盘被回退到旧内容，而工作区已 clean → 新内容永不重写）；仅当修订号
   未变（快照之后无新改动）才 `mark_clean` 并发布事件；写盘失败保留脏并**不发布
   事件**。
4. **「已自动备份」的唯一真相来源是后端事件**：`CoreEvent::WorkspaceSaved`
   （载荷 `workspaceId` / `revision` / `auto`）经 `main.rs` 的前端事件桥下发为
   `workspace-saved`，前端 `isDirty` 只在该事件到达时清除。store 侧用**两个修订号
   水位**判定：`lastPersistedRevision`（磁盘水位，事件推进）与 `lastPushedRevision`
   （编辑器水位，`update_workspace_file` 返回值推进）—— 仅当**磁盘水位 ≥ 编辑器水位**
   且无在途推送时才清脏（否则会假「已自动备份」或把指示器卡在「编辑中…」）。
5. **前端两级状态**：`syncPending`（未推送内存）与 `isDirty`（未落盘）分离；
   保存入口 `saveWorkspace` 一律「先推送在途改动，再落盘」（顺序反了会把旧内容
   写进磁盘），且仅当「推送成功 **且** 期间无新改动」才清 `isDirty`；`flushPendingSync`
   在推送期间出现新改动时同样不清 `syncPending`。

已知限制：`save()`（写锁）、`update_file`（写锁）与 auto-save 的写盘阶段（读锁）
都在持锁期间完成磁盘 I/O —— 编辑器同步在写盘期间会短暂阻塞。**2026-10-16 裁决
维持该设计**（原 P74-2）：锁内写盘是防「旧快照的写落在更新的写之后 → 磁盘回退且
永不重写」的唯一屏障，阻塞为毫秒级且被前端 2 秒防抖稀释；论证见
`doc/modules/src-tauri/service/workspace/manager.md` 的「持锁写盘与元数据取舍」。

> **2026-09-20 更新**：原「auto-save 开关与间隔需重启客户端才生效」的限制**已解除**（P48）——
> `static AtomicBool` 一次性标记改为 `WorkspaceManager` 的实例级状态，并由配置变更触发

**OJProvider 拆分为组合接口**

为避免单一巨型 trait，将 OJ 适配拆分为独立的小接口，各 Adapter 按需组合实现：

```
trait AuthProvider       // 登录、登出、会话管理
trait ContestProvider    // 获取比赛列表与详情
trait ProblemProvider    // 获取题目描述、样例
trait SubmissionProvider // 提交代码、查询评测结果
```

例如 `HOJAdapter` 同时实现以上四个 trait。后续新增 Adapter 时，可先只实现部分接口（以 `ProviderSet` 的 `Option` 字段注册，缺失能力查询时报 `ProviderNotFound`），逐步完善。

**OJ 身份、配置与注册均为数据**

接入一个新 OJ **不修改领域层**：OJ 身份是 `OjId`（字符串，会话文件名 `sessions/{id}.json`），不是编译期枚举；配置按 `OjInstance{id, baseUrl, enabled, options}` 实例清单组织（`oj.active` 指向当前实例，`contest_ref` 为不透明比赛引用）；适配器经 `AdapterFactory{id, build}` 工厂自注册进 `factories()` 清单。接入成本 = 1 个 adapter 子目录 + 工厂清单一行 + 配置一条实例。OJ 切换走显式 `switch_oj` 命令（切 Registry + 持久化 + 发布 `OJSwitched` 事件），与登录解耦；适配器构造依赖 `AdapterDeps` 只准 infra（http/事件总线/存储），禁止依赖 Service 层。

**Event 模块（核心解耦机制）**

`core/event` 定义 `CoreEvent` 枚举，建立在 `tokio::sync::broadcast` 之上（`CoreEventBus`），用于主程序内部解耦及插件共享事件流：

```
LoggedIn / LoggedOut / SessionExpired / TokenRotated
ConfigChanged / ThemeChanged / OjSwitched
ContestSelected / AnnouncementChanged / ProblemOpened
SubmissionCreated / SubmissionJudged
WorkspaceSaved
```

遵循原则：**查询与命令走 Service，状态变更发 CoreEvent 事实通知**。禁止将所有业务逻辑事件化。

**可靠性与职责分层（本节是判断「该走哪条路」的唯一依据）**

| 机制 | 适用 | 本项目落点 |
|------|------|-----------|
| **显式 Service 调用** | 必须等待结果的核心动作、同步前置条件 | 工作区落盘、OJ 切换清缓存、配置落盘、会话持久化、登出清理、用户域缓存回收 |
| **`broadcast`（CoreEventBus）** | 已发生事实的通知、低延迟刷新提醒、可丢失、可经查询恢复 | 前端桥、审计、PluginHost |
| **bounded mpsc + oneshot** | 需要背压与成功/失败回执的进程内请求/响应 | 当前**无真实需求，未引入**；出现「发送方要等结果且不想依赖具体 Service」时再引入 |
| **durable outbox** | 跨重启恢复、离线补发、失败重试、不可丢失 | 当前**未引入**；`sessions/` `workspaces/` `config.json` 的持久化本就由显式路径保证 |

**哪些动作必须显式完成**（不得依赖事件消费者）：保存工作区（含切换前保存旧工作区、关窗落盘、auto-save 循环调 Service 保存）、切换 OJ 前的内存缓存清理、配置落盘、凭证轮换落盘、登出清理、用户域缓存回收。

**哪些事件只是完成事实通知**：`WorkspaceSaved`（写失败或有新改动时不发）、`ConfigChanged`（落盘失败时不发）、`TokenRotated`（**仅在凭证落盘成功后**发布；无磁盘会话或写盘失败都不发）、`OjSwitched`、`LoggedIn` / `LoggedOut` / `SessionExpired`、`SubmissionCreated` / `SubmissionJudged`、`AnnouncementChanged`、`ContestSelected`、`ProblemOpened`、`ThemeChanged`。

**IPC 查询与前端轮询的职责**：真实状态（评测状态、公告内容、榜单、题目、提交列表/详情、会话状态、工作区真值）**只能**经 `IPC → Command → Service → Provider/Storage` 获取；前端轮询（公告 60s±10s、榜单 10s±2s、题目总览 30s±5s、评测状态）**必须保留**，它是事件丢失的补偿手段。事件只触发 UI 刷新，绝不作为状态来源。

**`Lagged` 后的恢复策略**：记录丢失数量 → 丢弃不可恢复的旧通知 → 调 `resync()` 查询当前状态 → 继续消费。**不能假设 `broadcast` 会自动补发**。`Closed`（总线析构）时消费者干净退出；消费者 panic 时按 `n × 200ms` 退避重启，上限为**连续 5 次**（`MAX_CONSUMER_RESTARTS`）—— 「连续」的判据是 worker 存活超 **30s**（`HEALTHY_RUN_THRESHOLD`）即视为健康运行过、重启计数归零：罕见但反复触发的 panic 不应累计成「永久放弃」，只有真正的崩溃循环才被上限拦住（代价是周期 ≥30s 的慢速崩溃循环永不放弃，属有意取舍）。

**Tauri Bridge 的生命周期**：在组合根（`main.rs`）经 `spawn_consumer` 启动，与审计、PluginHost 平级；`emit` 失败只告警（前端轮询会补齐）；**不阻塞任何 Service**（消费者与业务动作之间没有等待关系）。

**`CoreEvent` 与 `PluginEvent` 的边界**：插件只能收到 `PluginEvent`（经 `PluginEventAdapter` 白名单 + 字段裁剪 + 脱敏 + 版本化 `PluginEventEnvelope`）。插件**不得**依赖 `CoreEvent` / 内部 Service / 领域实体 / `broadcast::Receiver`。`PluginHost` 是适配与生命周期管理层，**不是第二套业务总线**。

**绝不能进入事件的信息**：Token、密码、完整 Session、认证头、源代码、内部文件路径、内部缓存对象、数据库连接信息、未脱敏用户实体、内部错误栈。

**消费者不能回滚已完成的核心动作**：业务动作在发布之前就已完成；`send` 返回「无消费者」不是业务失败。

**前端新增 Service 层**

前端分层由 `View → Store → Bridge` 调整为 `View → Store → Service → Bridge`：
- `Store`（Pinia）仅负责状态管理，不放网络请求、数据转换、缓存逻辑或业务流程
- `Service` 层封装所有业务逻辑（`contest.service.ts`、`problem.service.ts`、`submission.service.ts`、`workspace.service.ts`）
- `Bridge` 层封装 Tauri IPC 调用

**新增 ConfigService**

统一管理用户配置、OJ 配置、编辑器偏好、主题、布局及插件配置，避免配置逻辑分散。

**新增 ThemeService**

独立于 ConfigService，负责主题切换、配色方案、字体、圆角等 UI 参数管理，为后续主题扩展预留接口。

**兼容的外部系统**
- HOJ（开源 OJ 服务端，本项目首个适配目标）
- Qingdao University Online Judge (QDUOJ)
- HUSTOJ 及其衍生实现
- 支持标准 HTTPS 协议的 OJ Web/API 服务

## 5. 质量、非功能性需求与协作规范
5.1 非功能性需求 (NFRs)
- **性能要求**：
  - 系统应保证常用操作具有良好的响应速度。
  - 客户端启动时间不超过 3 秒。
  - 本地界面操作（界面切换、题面展示、代码编辑等）响应时间不超过 200ms。
  - 网络请求性能受目标 OJ 影响，但客户端应提供加载状态提示并避免阻塞界面。
  - 题面加载和提交结果查询应在网络允许条件下及时完成。
  - 客户端按**数据可变性**分层使用轮询与缓存，避免对同一份不变数据反复请求：
    不会变的数据（比赛元信息、题面、终态提交详情/测试点）走缓存；只由本人动作
    改变的数据（我的题目状态）走增量失效 + 按需重拉；随时可能被别人改变的数据
    （榜单名次、评测中状态、公告）只轮询，最多做同查询去抖。判据与失效路径见
    `doc/Architecture.md` 的「客户端缓存策略」。
- **可用性要求**：
  - 系统具备基本容错能力，在网络异常、OJ 服务异常或客户端异常退出情况下，保证用户代码和配置数据不丢失。
  - 自动保存用户代码；落盘语义与落盘时机（切题 / 失焦 / 页面隐藏 / 离开解题页 / 关窗 + auto-save 周期）见 §4.2「代码落盘语义（Workspace 持久化契约）」。
  - 支持异常退出后的工作区恢复。
  - 网络异常时提供明确错误提示。
  - 已加载题面可进行本地缓存（内存 + 磁盘，TTL 30 分钟，默认开启、可在设置页「OJ」分组关闭）；题目切换后保留切换前题目工作区内的代码。
- **安全性要求**：
  - 保证用户账号信息和会话信息的安全存储，不记录密码明文。
  - 日志记录避免泄露账号、Cookie 等敏感信息。
  - 可选实现所有网络通信采用 HTTPS。
  - 本地配置文件仅保存必要的用户数据。

**代码评审规范**

**测试策略**
| 层级 | 技术 | 覆盖范围 |
|------|------|---------|
| Rust 单元测试 | `cargo test` | Domain 层实体逻辑、各 Provider trait 默认实现 |
| Rust 集成测试 | `cargo test` (tests/) | 各 OJ Adapter 的请求/响应解析、Service 层编排流程 |
| 前端单元测试 | Vitest + Vue Test Utils | Pinia Store 逻辑、关键组件行为 |
| 前端 E2E 测试 | Tauri + Playwright（或 WebDriver） | 5 大核心功能闭环的端到端验证，使用 Mock OJ 后端 |

**前端测试文件组织**

单元测试与被测源文件分离，放置于同层目录下的 `__tests__/` 子目录，命名 `{module}.spec.ts`：

```
src/utils/
├── session-check.ts
└── __tests__/
    └── session-check.spec.ts
```

约定：
- 测试环境为 `node`，不引入 jsdom；需要 DOM API（如 `localStorage`）时用 `vi.stubGlobal` 打桩
- IPC 边界一律在 Bridge 层打桩（`vi.mock('@tauri-apps/api/core')`），单元测试不依赖真实 Rust 后端或 OJ 服务器
- 逐层隔离：测 Store 时 mock 其直接下游 Service，测 Service 时 mock 其直接下游 Bridge。"能否只 mock 一层就测"本身即分层是否正确的判据
- 时间与随机数通过参数注入（如 `planNextPrecheck(nowMs, startMs, rand)`），避免依赖 fake timers
- 运行：`npm test`（`vitest run`）；配置位于 `vite.config.ts` 的 `test` 字段
- 当前覆盖纯函数（`utils/`）、跨端错误契约（`bridge/`）与 Store/Service 状态机；组件测试（`@vue/test-utils`）尚未引入

**Rust 测试文件组织**

单元测试代码与源文件分离，放置于同模块目录下的 `tests/` 子目录，通过 `#[path]` 属性引用：

```
src/infra/
├── storage.rs                          → #[cfg(test)] #[path = "tests/storage_tests.rs"] mod tests;
└── tests/
    └── storage_tests.rs
```

约定：
- 测试文件命名：`{module_name}_tests.rs`
- 源文件引用方式：`#[cfg(test)] #[path = "tests/xxx_tests.rs"] mod tests;`
- 测试文件以 `use super::*;` 开头，可访问源文件内的 private 项
- 禁止使用 `src-tauri/tests/` 顶层集成测试目录覆盖单元测试职责，该目录仅用于跨模块集成测试

## 6. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 目标 OJ API 无公开文档或不稳定 | OJ Adapter 层开发受阻，需反复逆向工程 | 优先选取文档最完善的 OJ（如 HOJ）作为首个适配目标，验证组合 trait 设计的通用性后再扩展 |
| OJ 组合 trait 抽象粒度设计不当 | 接入新 OJ 时需频繁重构，破坏已有适配实现 | 完成首个 Adapter 后，接入第二个 OJ 前，基于两者差异审视 trait 边界 |
| Tauri 2 版本快速迭代，API 变动 | 升级时出现 Breaking Change，阻塞开发 | 锁定大版本，非必要不升级；关注 Release Notes 评估后再升级 |
| 团队 Rust 经验不足 | 后端开发效率低，错误处理不规范 | 核心逻辑优先在 Domain/Application 层以纯 Rust 实现，Infrastructure 层适度使用前端能力兜底 |
| 跨平台兼容性（后期扩展 Linux/macOS） | Windows 可用但其他平台存在渲染或系统 API 差异 | 全程使用 Tauri 官方跨平台 API，避免引入平台特定依赖；CI 启用多平台构建提前暴露问题 |

## 7. 插件系统架构

当前提供可运行的外围 JS 宿主：Manifest / API / 事件均为 v2。唯一 `CoreEventBus` → `PluginHost`（白名单/权限/128 有界队列）→ 每插件 QuickJS worker；Host 不执行用户回调，Manager 才管理生命周期，不存在第二套业务总线。

分层：`core/access` 显式撤销；`service` 只读身份/比赛/本人历史；`plugin/api|permission|query|execution_api` 安全 DTO、授权交集、作用域句柄/游标、有限 JSON 桥；`plugin/host` 事件边界；`plugin/runtime|manager` QuickJS 与生命周期；`infra/fs_plugin_repo + plugin_storage/http/notification` 实现仓库、存储、网络、通知；`commands/frontend` 开发入口。依赖方向 `infra → plugin`，`core/service` 不依赖 plugin（组合根除外）。

Manifest 声明不授权；`plugins.json` 在代码目录外，默认不启用；有效权限取交集。网络以精确 origin 为边界，全部 DNS 地址校验并固定；HTTP/私网需额外批准。禁止 Session Token、任意文件、进程和任意网络进入 JS。

完整架构见 [doc/plugin/architecture.md](plugin/architecture.md)。

## 8. 插件开发与限制

采用 rquickjs std/futures，单个离线 ES module；TS 用 esbuild 等在宿主外打包。每插件 16MiB、activate 10 秒、事件总计 30 秒；状态仅 `starting/running/stopped/failed`。插件可经 `hinina.log.*` 写宿主日志（无需权限，单条 1024B、每激活 30 条/分钟）。

- 插件作者：[development.md](plugin/development.md) + [tutorial.md](modules/src-tauri/plugin/tutorial.md)
- 契约：[contracts.md](plugin/contracts.md)（Manifest、审批、API、事件、查询、Runtime、错误、限流、IO）
- 路线图：[roadmap.md](plugin/roadmap.md)

本轮不实现气球业务插件。首次 AC 规则、历史去重/完整性、恢复状态、外部幂等和重试由插件完成。进程内引擎隔离不等于 OS 进程沙箱；本地文件系统写和已发 HTTP 不能保证停止回滚。
